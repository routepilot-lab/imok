## 流量卸载的实现前提

Linux 流表命中后会绕过后续转发钩子。硬件卸载还涉及异步下发和设备驱动，软件流表标记与硬件卸载标记应分别采集。测试需要观察已有流量是否停止，同时验证新的连接仍受保护。[Linux Netfilter 流表文档](https://docs.kernel.org/6.6/networking/nf_flowtable.html)

- 直连卸载只考虑已通过 fw4 转发策略且分类稳定的未受保护设备直连连接。仅调整转发链里新增流的匹配条件无法处理已有流表条目。
- 保护开启前，分别验证软件和硬件中的旧连接能清除，再允许界面显示「保护已生效」。保护期间必须阻止该设备的连接重新进入流表。
- fw4 重载期间需要覆盖从首个规则撤除到新表和保护状态重建完成的整段时间。单看重载完成后的规则和计数无法确认这个窗口。
- 当前的 fw4 接管放行规则可能先于用户的自定义转发限制。把流量送回原有的按 zone 转发路径，在生成链稳定且双向策略可核对的环境中可评估。需在目标固件检查自定义规则、返回链和 flow-add 顺序后才能判断兼容性。保持现有默认行为。

### 采样顺序

1. 在现有版本记录插件版本、配置备份、线路状态和测试设备路径。维护时段从现网包直接升级到汇总测试包，保留现网包用于回滚。
2. 核对 LuCI、正常线路、DNS 和设备接管。用独立测试设备确认 50 个未缓存查询均命中域名分流规则，采集错误和分类等待超时的前后差值。保存 WARP 启动 DNS 偏好后检查运行实例，随后按需重建并核对新实例。每次重建或切线恢复后，从同一个受管测试设备分别验证 DNS、国内直连和代理 HTTPS，并确认测试流量经过路由器的 imOK 分流。
3. 在同一公网出口完成协议及出口对比。覆盖严格探测失败后继续、取消、设置变化、恢复失败和重启后的恢复。逐项记录失败阶段和恢复的出口。
4. 验证现有断网保护和 fw4 重载，保留独立管理连接。持续抓包并对照连接跟踪，核对发生源端口改写的探测流。验证后检查线路、DNS 和防火墙恢复。

- MASQUE 和 WireGuard 分别记录出口、下载量、限额是否触顶、路由器 CPU，以及局域网客户端的对照数据。同一出口使用一致的目标、设备和采样时段。
- 卸载项分别验证软件和硬件。开启保护前建立长连接，记录两方向的流表状态。在界面确认生效后同时检查旧连接和新连接。fw4 抓包从重载前开始，到规则补齐且测试设备恢复后结束。任何漏包都记录时间和路径，并停止该轮、恢复防火墙配置。

### CPU 样本与离线规则样例

- 普通线路和出口、协议对比测速在下载窗口前后读取路由器 CPU 计数。记录整机平均忙碌率和最忙核心的平均忙碌率。计数不可用时结果中省略 CPU 值。CPU 数据包含同期在运行的其他任务。
- 可从仓库根目录运行 \`python3 packages/luci-app-routepilot/tools/offload_rule_preview.py --backend masque\` 或将参数改为 \`worker\`。输出同一组合成设备的现有规则与候选文本。候选仅将明确未受保护设备的两条提前放行规则限定为代理接口，直连两方向落回 fw4。它用于离线核对规则形状。驱动清理、真实转发和防火墙重载窗口按上表验收。
